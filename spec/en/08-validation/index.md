# 08. Validation

## 8.1 Overview

This chapter is the catalogue of validation rules for RUML documents. Every rule has a stable id of
the form `<PREFIX>-<NN>`; the sections group the rules by subject, and within a section the rules
are sorted by id. Implementations, error messages and test suites SHOULD cite these ids rather than
restate the rule text, so that a violation can be identified independently of language or wording.

A parser MUST reject a document that violates a rule of this catalogue. A rule that says "a parser
MUST accept …" states what the specification permits (MAY): a parser that rejects such a document
violates the rule. Rules of the layer `—` bind the tool that reads, writes or evaluates a file; they
are not properties of the file.

### Validation Layers

- **schema**: the rule can be checked by validating the document against the RUML JSON Schema alone.
  This includes the `format` keywords of the schema, such as `date-time`, `uri` and `regex`; a
  validator that does not assert formats does not check those parts.
- **semantic**: the rule needs logic beyond the schema, such as resolving references, comparing
  values or checking uniqueness across the document.
- **—**: the rule depends on the tool, for example on the capabilities it implements or on how it
  writes a file, and cannot be decided from the document alone.

A validation tool MUST check every rule of the layers `schema` and `semantic` ([`CAP-28`](#rule-cap-28)).

### Rule Ids

A rule id is never reused. A rule that is withdrawn keeps its row, marked _Retired_, and its id is
not given to another rule.

### JSON Schema

The JSON Schema is the normative structural definition of the format. It is maintained as a file and
is not restated here:

- **Source:** `schemas/ruml.schema.json` (draft 2020-12); RUML-EXT files are validated by
  `schemas/ruml-ext.schema.json`
- **Packages:** `@law-as-code-institute/ruml-schema` in the GitHub npm registry, `ruml-schema` on
  PyPI

The spec version the schema describes is carried in its `x-ruml-spec-version` annotation and
mirrored by the `$specVersion` value every conforming file MUST declare.

## 8.2 Scope

This catalogue covers the RUML document (`.ruml`) and the obligations of the tools that read, write
and evaluate it, including the obligations of a parser that processes RUML-EXT files (`CAP-22` to
`CAP-27`). It does not cover:

- the result file `.ruml-result` ([Chapter 5](../05-result-format/index.md));
- the RUML container, its hashes and signatures ([Chapter 7](../07-container/index.md));
- the requirements of [Chapter 4.5](../04-capabilities/4-5-ruml-ext.md) on RUML-EXT files other than
  the parser obligations;
- the contract of a spec-test runner ([Appendix A](../appendix/A-spec-tests/runner-contract.md)).

For `ruml:draft/` and reverse-domain capabilities, the extension points of
[Chapter 4.1](../04-capabilities/4-1-concept.md), this catalogue covers their declaration and use in
the document – id, `role` and `required` at the root, where and how often an entry may appear, and
that a node entry has a `payload` – but not the content of the payload, which is defined by the
parser and evaluator that implement the capability.

| <a id="rule-dp-14"></a>`DP-14` | 4.7.3           | schema   | `validation.min` and `validation.max` MUST have the type 4.7.3 gives for the data type.                                                                                                                       |
| <a id="rule-dp-15"></a>`DP-15` | 4.7.4           | schema   | An entry of `sets` MUST have `name` and `fields`; a parser MUST accept `description` in it and a DataPoint of `type: "object"` among its `fields`.                                                            |
| <a id="rule-dp-16"></a>`DP-16` | 4.7.4           | semantic | The `set` of a DataPoint MUST be the id of an entry of `sets`.                                                                                                                                                |
| <a id="rule-dp-17"></a>`DP-17` | 4.7.4           | semantic | A set MUST NOT reference itself, directly or transitively.                                                                                                                                                    |
| <a id="rule-dp-18"></a>`DP-18` | 4.8, 4.9, 4.14  | semantic | Every DataPoint id that the `expression` of a `ruml:query` or of a `ruml:expression` reads, and every id in `inputs.dataPoints` of a `ruml:ai-query`, MUST be a key of the `data` of `ruml:datapoints`.       |

## 8.9 Text Reference Rules

| Rule     | §         | Layer    | Requirement                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | --------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <a id="rule-txt-01"></a>`TXT-01` | 4.12      | schema   | The payload of a node's `ruml:text-reference` entry MUST have `refs` with at least one anchor. An anchor MUST have `id` and `type` (`represents` or `refers-to`) and MUST NOT have fields other than these and `element` (a lowercase UUID), which a parser MUST accept; a node MUST NOT have more than one `represents` anchor, and the same anchor MUST NOT appear twice. |

| <a id="rule-txt-04"></a>`TXT-04` | 4.12      | schema   | A text entry MUST have `title` and `timestamp`, and `status` unless it has `content`.                                                                                                                                                                                                                                                                                       |
| <a id="rule-txt-05"></a>`TXT-05` | 4.12      | semantic | In a text entry, `timestamp` and `validFrom` MUST be RFC 3339 date-times, `url` a URI and `language` an ISO 639-1 code.                                                                                                                                                                                                                                                     |

| <a id="rule-txt-07"></a>`TXT-07` | 4.12      | schema   | A text entry MUST NOT have both `text` and `content`; an embedded entry with status `inForce` MUST have a non-empty `text` or a `content`.                                                                                                                                                                                                                                  |
| <a id="rule-txt-08"></a>`TXT-08` | 4.12      | schema   | A text entry with `content` MUST have `digest`, `sha3-256:` followed by 64 lowercase hexadecimal digits.                                                                                                                                                                                                                                                                    |
| <a id="rule-txt-09"></a>`TXT-09` | 4.12      | semantic | `digest` MUST equal the SHA3-256 hash of the UTF-8 bytes of the RFC 8785 form of `content`.                                                                                                                                                                                                                                                                                 |
| <a id="rule-txt-10"></a>`TXT-10` | 4.12      | schema   | A text entry with `type` `url`, `container` or `external` MUST have `url`, `containerPath` or `ref` respectively.                                                                                                                                                                                                                                                           |

| <a id="rule-txt-13"></a>`TXT-13` | 4.12      | semantic | In a text entry with `content`, `status`, `validFrom`, `validUntil`, `language` and `version` MUST agree with the metadata of the text itself.                                                                                                                                                                                                                              |

| <a id="rule-txt-20"></a>`TXT-20` | 4.12      | semantic | The `element` of an anchor MUST be the `GUID` of an element in the `content` of the entry its `id` names; an anchor into an entry without `content` MUST NOT have `element`.                                                                                                                                                                                                |
